02

The two ways to fix it

This is the decision. Both remove every failure above; they differ in what the ids look like afterwards and how much moves.

option A · my pick

The columns become text

One migration changes those six columns from uuid to text. The app is not touched at all — every partner-… and inv-… id simply starts working.

  • Matches the rest of the database. Rooms, bookings, venues, channel links and the menu already store readable text ids — and the menu migration deliberately derives the same slug in SQL that the app derives. This makes the six leftovers agree.
  • Nothing is lost. A uuid stored as text is the same value, just in a wider box. Existing rows are untouched.
  • Small and self-contained: one migration, no app change, no risk of missing a spot.
  • Cost: ids stay readable rather than being opaque — which is what the whole app already does, so it is the consistent choice, not a compromise.
option B

The app starts sending real uuids

Leave the columns alone and change the six places that invent an id to make a real uuid instead.

  • Six files to get right, plus the seeded default inventory list, which already carries inv-1…inv-18 — those would need regenerating, and anything already pointing at them would need following.
  • Ids become unreadable (9f3c1a…), so a row in the database can no longer be recognised by eye — the opposite of how rooms, bookings and the menu work.
  • No migration needed for the column types themselves.
  • Risk: misses are silent. Any id-inventing spot I overlook fails exactly like the agency did — this whole bug is evidence that guessing the spots one at a time does not hold.
