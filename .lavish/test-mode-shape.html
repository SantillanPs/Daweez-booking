“Is it better to have it for everything?”

Yes — but only if it is a separate database. “Everything” is free that way, and much worse the other way.

With a separate database, isolation is not something you add table by table — it is what the thing is. With one flag across your own tables, every table you add is another place to forget a filter. So the answer to your question is really a choice between two shapes, and “everything” pushes you to the first one.

And one hard blocker a flag cannot solve

Your bookings table has two exclusion constraints. That is the database itself refusing to let two stays sit on the same room on the same dates — it is what makes double-booking impossible even if the app is wrong.

A test booking on Room 4 for a real date would collide with a real booking and be refused — and a test stay would block a real room. To allow that, those constraints have to be rebuilt to include the test flag, so test and real rows may overlap. Doable, but it is a change to the one thing protecting your calendar from double-booking.

The two shapes

AA separate database you switch to

The calendar’s toggle points the app at a second database with the same schema. Your test bookings, tabs, expenses and cleaning tasks all live there.

  • Everything is isolated at once — nothing to filter, nothing to forget, no constraint to touch.
  • Your real rate card, menu and settings are copied in once, so tests use real prices.
  • The exclusion constraints keep working — in the test database — so double-booking is still tested properly.
  • Cost: a second database to create and keep in step when the schema changes. Supabase branches are built for exactly this (I did not create one — it can carry a cost, so that is your call), or a second free project works too.

BOne flag across your own tables

A test flag on the eight work tables, every read filtered by the current mode, and the two booking constraints rebuilt to allow test/real overlap.

  • No second database to keep in step.
  • Eight tables, and every read and write of each one needs the filter. Availability checks, the earnings report, the bookings list, receipts, the calendar, the restaurant till, housekeeping — all of them.
  • One missed filter is a test expense in your real profit, or a test stay shown to a staff member as a real guest.

The risk both shapes share, and the thing to design around: being left switched on. If a staff member takes a real booking while test mode is on, it lands in the test database and is lost. So whatever we pick, test mode needs a loud banner across the screen, a way to see at a glance that it is on, and it should switch itself off on reload — never survive in the background overnight.

One decision

A or B?

My recommendation: A. You asked for “everything”, and A is the only shape where everything is covered without adding a filter to every table — and it is the only one that leaves your double-booking protection untouched.
