# Frontend (React + Vite Client) AGENTS.md

## Purpose

This directory contains the React + TypeScript frontend codebase for the Daweez Pension House property management system (PMS) staff dashboard and the guest-facing direct reservation portal.

## Ownership

- Primary Owner: Frontend Engineers / Antigravity Agent
- Scope: Handles UI rendering, user interaction flows, client-side state/caching, local storage fallback database, and API interactions with Supabase.

## Local Contracts

- **State Management & Routing**: Uses React state coupled with `@tanstack/react-query` to handle fetching, caching, and mutating, `@tanstack/react-router` for view-tab routing and layout hierarchies, and `@tanstack/react-table` for sortable, searchable data grids. Booking data is synchronized instantly over a WebSocket using a Supabase Realtime subscription via `useRealtimeBookings.ts` to replace high-frequency polling.

## Work Guidance

- **Styling Rules**: Use Tailwind CSS variables. Keep the curated "Sun & Sea" palette consistent — sand paper (`--bg-page #FAF6EE`, body `#F0E9DA`), sea-teal actions (`--brand-primary #2E7D78`, ring `#57A49C`), sun gold accents (`sun-400 #DEAE55` / `sun-500 #C9922F`), coral for "needs attention" (`coral-500 #D9604A`), foam-white cards (`--bg-card #FFFFFF`). The `--brand-*` CSS vars map to sea teal so existing components restyle automatically; hardcoded gold hexes are legacy. Fonts: Sora via `font-display` for headings, DM Sans via `font-sans` for body. Avoid raw inline styles. Use `rounded-lg`/`rounded-xl` from config. Minimal shadows: `shadow-soft` on cards, `shadow-softLg`/float for modals and floating bars, `shadow-sheet` for slide-over panels. **daisyUI v4** is installed and the **booking form** (`WalkInBookingForm` + its walk-in subcomponents: RoomDetailsForm, AmenitiesForm, DiscountPricingControls, BillingSummary) uses daisyUI component classes (`btn`, `input input-bordered`, `select`, `checkbox`, `card`/token classes like `bg-base-100`/`text-primary`/`text-success`) with a custom **`sunsea`** daisyUI theme (maps the Sun & Sea palette + rounded corners) via `data-theme="sunsea"` on `<html>`. The rest of the app keeps the custom Sun & Sea palette. Register: `plugins: [require("daisyui")]` + `daisyui: { themes: [{ sunsea: { ... } }] }` in `tailwind.config.js`.
- **Dashboard Grid Layouts**: When creating 2-column split views (e.g. Form on the left, Data Ledger on the right), wrap the page title and description within the left column container. Do not span the title across the top of the grid, as this pushes the data column down and breaks vertical centering.
- **Settings Space Efficiency**: For repetitive configuration sections (like room settings or long URLs), prefer dense accordion lists over stacked padded cards. Use absolute-positioned action buttons (e.g. copy icons) embedded directly inside input fields to save horizontal space.
- **Readability & Badges Column Layout**: Do not apply restrictive max-width constraints to table columns that display badges or tags. Overrides and status indicators must render in clear, well-spaced badges using brand accent tokens (`brand-text`/`brand-bg`/`brand-border`, sea teal) for maximum readability.
- **File-Size Flag**: `ExtendStayModal.tsx` and `WalkInBookingForm.tsx` exceed the 300-line limit and are flagged for refactoring into subcomponents (per the project file-size rule). `CorporateBookingForm.tsx` was extracted from `WalkInBookingForm` to keep booking concerns separate.
- **Bookings Start Unpaid (Option B)**: The booking form records the guest's payment plan, but a new booking is saved with no money received (unpaid, owes the full amount). Money is only counted — and a Payment Receipt printed — when staff record a payment via "Record a payment" on the booking. This keeps the plan separate from the confirmed payment and avoids counting a payment twice.
- **Free-Typing Number Boxes**: Money/quantity inputs use the shared [NumInput](file:///c:/Users/dev4s/Documents/Programming/Daweez/src/components/NumInput.tsx) (or a plain `type="text"` + `inputMode` box). Never use `type="number"` — the OS spinner and its "snap back to 0 on backspace" behavior confuse staff. NumInput types freely (Backspace clears it, can be empty) and still reports a clean number via `onChange`.
- **Money-First Payment Display**: Staff-facing payment info must read like plain language, never accounting columns. Use big, bold, color-coded labels — vibrant green for "Paid", amber for "Partial · ₱X left", strong red for "Owes ₱X" — via `utils/bookingMoney.ts`. Keep the single most important money number (e.g. "Who owes right now") visible at the top of money-related lists.
- **Always Apply UX Best Practices**: Every UI must be usable and space-smart by default — high information density, no wasted white space (never leave a dead row next to a small control), minimal scrolling (no "box on box" stacking), progressive disclosure (show rare/secondary options only when relevant; default to the common path rather than forcing a choice), multi-column/responsive grids to use horizontal width, clear labels/affordances/feedback, and accessibility. Prefer familiar patterns and keep it compact.
- **Report extras are configurable per group (Earnings Report)**: The report's **Extras** column shows a flat staff-editable amount per category group — **Rooms + Vacation House** share one (`RateConfig.accommodationExtras`), **Garden + Gazebo** share another (`RateConfig.venueExtras`), set in **Settings → Shared Rates**. These REPLACE the per-category extras figure (rooms no longer itemize booking extras in the summary; venues' "Included" becomes this amount) and are ADDED to each category's total. A category's Room Rate column stays the base, so Extras + base = Total. Per-room drill-down rows still show their real booking extras.
- **Inline Required-Field Validation**: Booking forms validate required fields per field, not as one message at the bottom. Required boxes keep a red `*` label, get a red border (`border-coral-400`), and show a short red note right under the box when left empty — it fires live on blur and again on Save (mark empty fields with a touched/trySave flag). This keeps the note where the problem is instead of a single generic error.
- **Responsive Design**: Desktop-first layout. Top tab nav is the primary navigation. The UI is built for larger screens first with responsive adaptations for mobile. Bottom tab nav appears on mobile (`md:hidden`), while top tabs are always visible on desktop (`hidden md:block`). Tables use `overflow-x-auto` for horizontal scrolling on small screens. Calendar cells use responsive min-heights (`min-h-[80px] sm:min-h-[100px]`). On the `/calendar` route, the layout is viewport-locked (`h-screen overflow-hidden`) to eliminate dual scrollbars, keeping top controls and table headers stickily anchored while allowing the grid table itself to scroll horizontally and vertically.
- **Paper Guest Registration as Reference**: The staff-familiar paper Guest Registration form (Daweez Pension House) is the reference for the walk-in booking UI and the printed Guest Billing Statement — same fields (Birth Date, companion Name/Nationality/Breakfast), payment methods (Cash/Gcash/Bank Transfer/Other), Pension Policies, standard check-in/out times, and a Guest Signature line. Keep the digital form faithful but simple so staff recognize it.
- **Standard Check-in / Check-out Times**: Check-in is 2 PM and check-out is 12 PM by default. The Check in / Check out buttons compute early/late hours automatically against these (configurable in Settings→Rates as `standardCheckInTime` / `standardCheckOutTime`). Early/late is charged **only at the actual check-in/out** (rooms ₱/hr up to `lateEarlyCapHours`, then one full night; venues charge the venue hourly rate, e.g. ₱500/hr, hourly for any overlap incl. Gazebo & Garden) — never during booking, because the arrival/departure time isn't known yet.
- **Double Booking Prevention**: Any transaction or booking action must run collision checks through `isRoomAvailable` or `isVenueRangeAvailable`. Check-in dates must be chronologically earlier than check-out dates.
- **Group Selection Mode**: When booking multiple units in Group Selection Mode, each unit has its own check-in/out date range selected sequentially on the timeline grid (2 clicks per unit: check-in → check-out). Toggling or selecting ranges runs immediate collision checks; conflicts trigger warnings but do not clear the active selection list. Picks accumulate silently (no floating selection bar); the **New booking**, **Corporate**, and **Log old booking** buttons stay disabled until at least one unit/date range is picked, then clicking the enabled one continues into the full booking form (or the corporate form) with those picks. Launching any booking action — **New booking**, **Corporate**, or **Log old booking** — clears the picked selections off the calendar so they don't stay highlighted after.
- **One Booking Process**: The single booking form is `WalkInBookingForm` (a 3-step wizard; the individual flow, partner uses `CorporateBookingForm`), used for every way of creating or editing a booking (New booking button, click-empty-day, group selection, and editing). The room/dates come from the calendar pick (the entry point); the modal header has a **Booking / Block dates** toggle, and Block is a secondary action that shows a compact block-only mode. Step 1 captures guest information (Name / Contact No. / Nationality / Address) + companions; Step 2 captures Add-ons & Discount + Receptionist on duty; Step 3 captures the read-only Billing summary (Total / Deposit / Balance), then Confirm. A new booking is saved **not yet paid** (Option B); money is counted only when staff record a payment via the post-create **Record a payment** control (which appends a `PaymentRecord` and prints a Payment Receipt). `createManualBooking` stays the single write path (collision checks + pricing inside).
- **Old Booking Backfill (paper logs)**: Use the calendar toolbar's **Log old booking** to import a historical paper booking. The system still assigns its own sequential `invoice_number` (GRF-YYYYMM-NNNN), and the original paper log number + date are stored in `reference_number`/`registered_on` and included in the bookings-list search (so staff find a booking by guest name, the system number, or the old paper number). What was paid is recorded via `downpayment_paid` / `balance_due` / `payment_status` and a `payment_records` entry. The form accepts **multiple rooms/venues** at once (pre-filled from the calendar selection). The **Total is auto-computed** across all selected units (each unit's nightly rate × its nights), with a **Use Promo Price** toggle to choose Regular or Promo (defaults to Regular) — staff only type the amount actually paid, which is split proportionally across the bookings; contact number is optional (a paper log may have only a guest name).
- **Per-Day Breakfast (not planned ahead)**: Breakfast is **not** chosen at booking time. Staff record it day-by-day during the stay in the booking details modal (`BreakfastRecorder`) — pick the day, a meal from the staff-editable menu (`getBreakfastMenu()`), and how many people; each entry stores its price so the menu can change later without re-pricing. It's added to the balance and appears on the billing statement at check-out. Old plan-ahead bookings still bill via the legacy path.
- **Null-Safe Pricing Reads**: `calculatePricing` treats `null` like `undefined` for `breakfastOrders` (DB round-trips turn missing arrays into `null`); callers passing stored booking fields into the invoice must normalize `null` arrays (PrintInvoiceModal maps `null` → `[]`) so re-priced invoices never crash or invent charges.
- **Local Date Strings (timezone-safe)**: Booking dates (`check_in`/`check_out`) are plain `YYYY-MM-DD` calendar-day strings. Always build them with `dateToString(date)` from `utils/helpers.ts` (local components) — never `.toISOString().split('T')[0]`, which shifts dates back one day in UTC+8. This applies to calendar cell keys, booking creation/confirmation, "today" comparisons (briefing, dashboard stats, bookings list), and date-input defaults/minimums.
- **Regular/Promo Pricing**: Each room/venue stores a `base_price` (Regular) and optional `promo_price` (exact sheet price). The nightly rate is `promo_price` when `usePromo=true` else `base_price`; `calculatePricing({ usePromo })` reports `discountAmount`/`discountPercent` from the exact regular-vs-promo delta (not a fixed 20%). The website uses promo only while the global `promoMode` flag is ON and persists `promo_applied` onto the booking; the walk-in form uses a per-booking **Use Promo Price** toggle that likewise persists `promo_applied`; old automatic 20% for `website/manual/facebook` is removed. Read paths (invoice, analytics) recompute via `booking.promo_applied` so historic and new invoices remain stable.
- **Offline / Local Fallback**: Code must check `isSupabaseConfigured` and seamlessly fallback to local storage DB endpoints (`l_etoile_bookings_db`, `l_etoile_feeds_db`) to guarantee runtime persistence without a live database.
- **Background Calendar Sync**: Third-party bookings (Airbnb/Booking.com) must sync automatically via iCal feeds in the background upon mounting the application and at regular intervals (5 minutes) thereafter, with a manual OTA Sync trigger as a backup.
- **Staff Passcode Authentication Gate**: The staff portal is protected by a client-side passcode authentication gate. Authorized passcodes include 'daweez2026' (case-insensitive), '8888', and any custom passcode defined in VITE_STAFF_PASSCODE. Successful authentication persists in localStorage as `daweez_pms_auth` until explicit logout.
- **Performance Guardrails for Grids & Complex Views**:
  - **State Isolation**: High-frequency states (e.g. mouse hover coordinates, hovered dates, range calculations) must live at the lowest leaf component level possible. Avoid placing hover states in orchestrators or context providers to prevent wide component trees from re-rendering.
  - **Memoized Cell Wrappers**: Wrap individual grid cells or list items in a memoized component wrapper (`React.memo`) using strict custom equality comparators to bypass rendering. Ensure callbacks are stable or checked appropriately, converting $O(N)$ re-renders to $O(1)$ changes. A memo comparator MUST compare every prop that affects the rendered output or an onClick closure (e.g. the cell's `date`, `isoStr`, `id`), and key dynamic lists by stable data identity (e.g. the day's ISO string), NOT array index — otherwise a reused component instance keeps a stale value in its handler after data changes (this caused the timeline to sometimes save a wrong, month-shifted check-out date like Aug 20 when July 20 was clicked).
  - **Numeric Timestamp Operations**: Avoid using string parsing operations (like `.toDateString()` or `.toISOString()`) inside rendering loops. Convert dates to numeric timestamps via `.getTime()` for cheap integer comparisons.
  - **Keystroke Rendering Isolation**: Keep text field keystroke states isolated so typing in registry forms does not trigger re-calculations or re-renders of adjacent sidebar receipts and summaries.
  - **Avoid Backdrop Filter Penalty**: Do not apply `backdrop-filter: blur(...)` styling to modals or overlay backdrops rendered on top of dense grids or tables. This triggers heavy GPU composition paint operations on every keypress or state change. Use solid or semi-transparent flat colors instead (e.g. `bg-slate-900/50`).
  - **Debounced Hover Tooltips**: Details tooltips on dense timeline grids must be debounced with a short delay (e.g., `500ms`) using a `useRef` timeout to prevent rendering spam when moving the mouse across cells. Stale timeouts must be cleared on mouse leave and on component unmount.
  - **Floating UI Alerts over Inline Banners**: Transient states (such as active scheduler selection status) must be presented in absolute/fixed floating elements (toasts) rather than inline blocks to avoid grid layout shifts, vertical screen clutter, and component displacement.
  - **Lazy-Route Dependency Pre-Bundling**: Dependencies reachable only through a lazy-loaded route (e.g. `@tanstack/charts` on `/analytics`) must be listed in `vite.config.ts` → `optimizeDeps.include`. Otherwise Vite discovers them on first navigation and answers `504 Outdated Optimize Dep`, which fails the dynamic import with `Failed to fetch dynamically imported module`.
