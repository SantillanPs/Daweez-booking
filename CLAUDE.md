# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A staff system for **Daweez Pension House** (Tandag City, Philippines): 10 rooms and three venues (Vacation House, Gazebo, Garden Area). It replaces a paper booking process. Three parts, in priority order: **bookings** (closest to done), **restaurant and bar till**, **stock room**. The staff are not technical — every label is plain everyday English ("Total Money In", never accounting terms), the UI states facts without captions explaining them, and there are no browser `alert`/`confirm` pop-ups (use `showToast` and `askConfirm`).

React 19 + TypeScript + Vite, TanStack Router/Query, Tailwind 3 + DaisyUI, Supabase (Postgres, Realtime, three edge functions). Deployed on Vercel.

## Architecture

### How the app reaches the database

- The app uses the public anon key. "Login" is a passcode checked in the browser that sets a `localStorage` flag — there are no staff accounts yet (board card k74).
- **Bookings cannot be written directly.** anon has SELECT only; every write goes through SECURITY DEFINER functions: `book_booking`, `update_booking`, `cancel_booking`, `delete_booking`, plus narrow single-column writers (`set_booking_agreed_deposit`, `set_booking_stay_hours`, `undo_booking_check` — the last no longer called, since there is no check-in). Room prices and `app_settings` follow the same pattern. Tabs, menu, stock, expenses and agencies are written directly — except the lines on an order slip, which go through `apply_order_changes` (see Restaurant).
- **When the database can't be reached** (2026-11-06) `ConnectionBand` shows under the top bar on every staff screen, and the calendar fades back a little and, with no rooms, says so. `utils/connection.ts` decides it: the browser's offline event, or a call that got no answer — the client's `fetch` (`supabaseClient.ts`) reports every call, so nothing else needs to. While lost it asks again every 10 seconds; once back it reads every query again. A read that fails must **throw**, never return an empty list, or the screen loses what it had (`getBookings` did, and cleared the calendar).
- **Ids are text** (`room-3`, `venue-gazebo`, `partner-…`). Never cast an id to `uuid` inside a database function. Only `tabs` and `tab_lines` use real uuids.
- Double booking is refused by exclusion constraints on `bookings`, counted in **half-days** (`booking_halves`, mirrored by `bookingHalves` in `utils/halfDays.ts` — change both together); the client check (`utils/availability.ts`) is only an early warning. Cancelled bookings are excluded from both.

### Booking data flow

`utils/db.ts` (reads/writes) → `hooks/useBookings.ts` (TanStack Query cache + mutations) → `DashboardContext` → tabs. `hooks/useRealtimeBookings.ts` patches the cache from Supabase Realtime.

- **A booking column must be added in four places:** the `Booking` type, `toBookingRecord` (db.ts), the reader in `getBookings` (db.ts), and `rowToBooking` (useRealtimeBookings.ts). The cached booking is what gets saved back, so a column missing from a mapper is wiped on the next save.
- **`update_booking` takes the whole row.** JSON columns sent as `null` are written as empty (the `COALESCE` in the function does not protect them). Any save path that builds a booking from scratch rather than from the cached row must carry over what it does not own — see the edit branch of `createManualBookingMutation`.
- The context exposes `bookings` (active stays; cancelled left out) and `allBookings`. Use `allBookings` only where cancelled bookings matter: the Front desk's History (`DeskHistory` — bookings made and check-ins and outs only) and Bills & receipts (`BillsReceipts`, `/bills` — every statement with a Paid / Part paid / Not paid / Cancelled / Rescheduled filter — a booking whose check-in day moved on the bill keeps its first dates in `bookings.moved_from`, written only by `set_booking_moved_from` (`utils/movedFrom.ts`) — every receipt, a payment's fixes and removal; 2026-10-29), the daily money sheet, and receipt numbering.
- A booking of several rooms is **one row per room/venue, each with its own `invoice_number`** (the column is UNIQUE), tied together by a shared **`group_id`** written by `set_booking_group`. Ask `groupOf(booking, list)` (`utils/bookingGroup.ts`) which rooms belong together — the bill and the booking panel both do. The bill carries the first room's number. **Every room of a bill shows the bill's money** (`asBill`: the pill, its hover card and the panel's figure, 2026-10-20); **the bill's money is shown on its first room still in the hotel** (2026-11-07): its discounts and what it still owes, worked out by `settleBill` (`utils/bookingBalance.ts`); the other rooms hold 0 / 0. Cancelling or deleting that room settles the rest again (`settleWithout` in `useBookings`), so the next room takes over. A bill saved before then (a slice on every room) is moved over the next time it is settled (`onLead`).

### Money

- **One pricing rule:** `calculatePricing` in `utils/pricing.ts`. A **saved** booking is priced only through `priceBooking` (same file) — the balance, the bill, the ledger and the report all call it, so a fact added there reaches rooms, venues, short stays and agencies at once; `scripts/check_one_pricing.cjs` fails if another file calls `calculatePricing` (only a not-yet-saved form may: the booking save, the public page). **A bill's discounts come off its whole total, like a payment** (2026-11-11): every room's `grandTotal` and its food (`billStays`); `scripts/check_bill_total.cjs` fails if a line the statement prints is out of their reach — a new kind of charge goes into `calculatePricing`'s total too. `settleBill` in `utils/bookingBalance.ts` is the one place "what is owed" is worked out, for the whole bill: every room's stay + food − the discounts − money received.
- Payment status is derived from recorded payments, never typed. **A booking's payments live in the `payments` table, one row per receipt, under the bill** (`bill_id` = `group_id`, or the booking's id; Sebastian, 2026-11-09: "have payments its own place"), so cancelling or deleting a room can no longer take a bill's receipts with it. The app still reads and saves them as `payment_records` on the booking: `withPayments` (`utils/payments.ts`) hands each bill's payments to its first room still in the hotel, and the trigger `file_booking_payments` files whatever a save sends and leaves `bookings.payment_records` empty — so every save path writes payments as before (`payOnBill`, `withFixedPayment`). Taking one back is `removePayment` (`remove_payment`: marked `removed_at`, never deleted, so a stale save cannot bring it back). `set_booking_group` moves a booking's payments to its new bill. Each has a receipt number `PR-YYYYMM-NNN` unique across `payments` (removed ones too) and the tabs' `payment_records`, which diners' slips still keep on the slip. A `share` on a record is only on bills saved before 2026-11-07.
- Dates are built from **local** time parts (`dateToString`), never `toISOString()` — the hotel is UTC+8.
- `settleBill` leaves a bill untouched when its room is not in the list it was handed (the page is still loading) and when it is a block. Do not re-price with an empty `rooms` array: `calculatePricing` finds no price for a room that is not in the list (the built-in sample rooms were taken out on 2026-11-06, with the app's no-database mode — without `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` it shows only "This copy isn't set up", `isSetUp` in `main.tsx`).
- A stay **billed to an agency** (`isBilledToAgency`: has `partner_deal_id` or `company_name`) is not chased for money. It is left out of what the desk chases and listed under "Agencies owe" (`isOwedByAgency`). Plan `'agency'` ("Bill the agency") is no longer offered: since 2026-10-06 the form has three deposit choices for every booking — `custom` (shown as **Deposit** since 2026-10-21; half the stay filled in, with a note kept in `bookings.notes`), `full`, `reservation` (No deposit). `'agency'` and `'deposit'` are only read back from older bookings and shown as No deposit and Custom.
- A room's breakfast is charged once for each morning of its stay, or only for the mornings the desk picked on the bill (the Breakfast line's two dates, `MorningPick`, 2026-10-29), kept in `bookings.breakfast_days`. Ask `breakfastMornings` (`utils/breakfast.ts`): days outside the stay do not count, and none (or none left after the dates moved) is every morning. `calculatePricing` takes them as `breakfastDays`, so every caller that passes `breakfastIncluded` passes them too; the breakfast cup asks only on those mornings.
- What the guest said for the stay (food, time) is `event_addons.breakfast_plan`, per room, set under the room's switch in the bill's Breakfast pop-up (`BreakfastPlanLinks`; never required) and, for the time, on the booking panel (`calendar/BreakfastMornings`). It is only a starting point (`morningItems`). Each morning's breakfast answer is `bookings.breakfast_choices`, written only by `set_booking_breakfast_choices` (`utils/breakfastChoice.ts`). It is a record, not a charge — never put it in `breakfast_records`, which the pricing rule bills. **The kitchen cooks only what the desk confirmed** (Sebastian, 2026-11-01): `sent_at` is stamped when the desk presses Serve or Nothing (`calendar/BreakfastPicker`), a later morning changed ahead of time has none and is still asked on its day (`isConfirmed`), `KitchenTab` shows today's confirmed answers with dishes that have no `ready_at` as cards, soonest time first, and "Order ready" stamps it. Both live inside the JSON, so there is no column for them. **The owner's rule (2026-10-08): once a feature works, how it feels comes before everything else** — the breakfast window's moves (`bp-…` in `index.css`) are the model.
- **Today's money is a balance that carries over** (`buildDailyReport` in `utils/dailyReport.ts`, the one rule behind the screen and the printed sheet): its bottom bar is the staff's own paper summary, line for line — Cash for today (`totalIn`) · Add: Cash balance forwarded (`broughtForward`) · Less: GCash, bank & cheque (`totalNotCash`, only on a day there was some; it never carries over, 2026-11-07) · Cash on hand · Less: Expenses (`totalOut`) · Less: Cash remitted · Total cash on hand (`balance`). Money the staff hand to the owner is a row in `money_handovers` (`utils/handovers.ts`, `expenses/HandOverModal`): it comes off the balance but is **not an expense**, so nothing in the earnings report reads it. It is rare, so it is a quiet link under the day and its gold line shows only on a day it happened. Cash the staff put into the hotel ("Add cash on hand") is the same row with `kind = 'in'`: it adds to the balance and is never income. Each Money in line is a payment receipt (`MoneyInLine`, `PaymentLine` in `expenses/DayMoney`): a booking's opens its bill right there, being worked on (`calendar/WorkingBill`: the bill over its panel kept out of sight with `unseen`, since the payments go through the panel; the tapped payment is ringed, `mark` → `.bill-mark`, and folded payments open; the top bar's **Booking** (`onBooking` on `StatementShell`, not on a cancelled booking) hands the booking to the calendar through `focusBookingAfterCreate`, which opens its panel and pulses its pill), a diner's slip its receipt. Its pencil opens `expenses/PaymentEdit`, a small slip under the line that fixes what it was for, the amount, how they paid and the day (`fixMoneyIn` in `ExpensesTab`: a booking's through `withFixedPayment` on every room holding the receipt, a slip's through `saveTabFix`, which also moves a hand-written sale's one line; a real diner's lines keep their prices; a new day's message has Undo; 2026-11-01). The slip's bin turns into Remove and takes the payment back the way Bills & receipts does; a hand-written one is deleted through `remove_hand_sale`, since anon cannot delete a slip (2026-11-03). An expense has the same pencil and slip (`expenses/ExpenseEdit`: note, amount, what it was for, the day, Remove). Under Money out, a day's expenses of one category are one line with a count (`ExpenseGroup`, `byCategory` in `expenses/DayMoney`) that opens to every expense and its note; the printed sheet still lists each one. A day's payments on one bill are one line with a count and the bill's number (`PaymentGroup`, `byBill` in `expenses/DayMoney`, keyed by `MoneyInLine.bill`, the bill's first room's `invoice_number`), opening to each payment; a diner's slips from one table are grouped the same way (`groupKey`, 2026-11-06); a lone payment shows its bill number beside the room, and the printed sheet still lists each one. Lines sharing a receipt number are one payment across rooms, a payment on a cancelled booking stays on its day scratched off with the day it was cancelled (`MoneyInLine.cancelled`, `.dm-scratch`) and counts in no total or carried balance, nor in the Earnings report, 2026-10-29; but a diner's slip is never joined to a booking's payment, and a room's receipt number is read fresh from the database (`freshReceiptNumber`) so it cannot take a slip's.
- **There is one bill, always being worked on** (Sebastian, 2026-10-24: "no more view billing or receive money. merge everything"). The panel's one **Bill** button, a statement found by search and a booking just made all open `calendar/NewBookingBill` with `editing` set, over the panel (`billOf` in `CalendarTab`). Each change is saved by itself (5 seconds after the first change, or as the bill closes; one queue; `✓ Saved` on the top bar) through `submitBookingForm`; its payments go through the panel beneath it (`PanelDesk` on `deskRef`, so `payBill` puts them on the bill's first room), and the paper copy for Print and Email is a hidden `PrintInvoiceModal` (`.bill-paper`). It is never only looked at (Sebastian, 2026-10-28): a cancelled booking found by search opens it the same way. Cancel asks why (a quick reason, the desk's words, or both; `cancel_booking`'s `p_note` → `bookings.cancel_note`, which `update_booking` never touches), and a cancelled bill wears a red CANCELLED stamp with the day and that note, on screen and on paper (`billing/CancelledStamp`); saving a cancelled bill keeps it cancelled. The bill's blank lines (`billing/BillDesk`): a payment is written on its blank line (what it was for — `PaymentRecord.purpose`, printed on the bill and the receipt — and the amount, then how they paid; always dated today) and a charge added under its rows (`event_addons.charges`, `BillCharge` — priced by `calculatePricing` like the add-ons). The statement's payment details, policies and signatures show only on paper (`data-paper`; the emailed copy shows them too). An agency's paper stays Total only.
- **A bill can have several discounts, each with a note** (2026-10-29): `bookings.applied_discount` holds a list (an older row holds one object — read it with `discountsOf`, `utils/discounts.ts`). The bill's first room holds the whole list, taken off all its rooms' stays together (`billStays` in `utils/pricing.ts`, passed to `priceBooking` as `stays`); a bill saved before 2026-11-07 held a slice of each on every room, which the statement still joins by place (`StatementLineItem.slot`, `mergeDiscountRows`). The bill shows them as one `Less: discount` line that opens to each (`DiscountsPop` in `NewBookingBill`); the paper prints one row each.
- A block with no end date is an ordinary block whose `check_out` is `OPEN_END` (`utils/openBlock.ts`).

### Screens

- **Calendar** (`CalendarTab`) is the landing screen and the only way to start a booking: pick dates on the grid, then the action bar offers New booking / short stay / block / log old booking. The search button on its top line (`calendar/CalendarSearch`, 2026-10-24; "/" opens it) finds bookings by guest or room, billing statements by `invoice_number` and receipts by receipt number, cancelled ones too: a booking opens its panel on the calendar (`openFound` pulses its pill), a statement or a receipt opens its print window, and a cancelled booking opens its statement. `calendar/ExtendStayModal` is the booking panel: where the stay is, the money in one figure, the Bill button and Cancel. **There is no check-in or check-out** (Sebastian, 2026-10-20: on paper the staff only ever recorded the booking, the guest and the money, and the app must not change a booking by itself): where a stay is comes from its dates against today (`utils/stayStage.ts` — before, during, after; the arrival day is during, the leaving day after; a noted check-out makes it after at once, 2026-10-25), and early or late hours are a charge the desk adds to the bill. Never write `tab_lines` from the tablet one call at a time, and never lock the menu while saving. `useOpenSlips` reads every open slip with its lines in one query and throws away a read that an order overtook. **The order reaches the kitchen on a screen, never on paper:** "Send to kitchen" marks the lines sent, and the cook reads them on Restaurant → Kitchen (`KitchenTab`, `/restaurant/kitchen`, `useKitchenQueue` over the `kitchen_queue` view), which stays open on the kitchen's own device. A line counts four things in a row — `qty` → `sent_qty` → `ready_qty` → `served_qty` — each never more than the one before, written by `mark_order_lines_sent` / `_ready` / `_served`. The kitchen's list ignores whether the slip is still open: a guest who pays first still gets their food. A kitchen card is a checklist: a ticked dish is saved as cooked at once but stays on its card struck through (that memory is the screen's own, in `useKitchenQueue`) until the whole card is done; the waiting time turns gold at 10 minutes and red at 15 (`KitchenTab`).
- **The paper slip** (`restaurant/PaperSlip`, 2026-11-11; a popup on Orders since 2026-11-12, opened by `PaperSlipButton` at the top right of the empty slip and of the phone's order bar; `/restaurant/paper` redirects to Orders): the restaurant takes orders on paper, so a slip is copied in afterwards — the name first (or, with the bed switch, a search over every stay not over yet, by name only), then the dishes ("2 adobo"; a dish not on the menu takes a typed price), then how it ended. `savePaperSlip` (`utils/tabs.ts`) saves it as a real order slip through `openTab` + `apply_order_changes` (stock comes off), marks every line sent, cooked and served, then either pays it (`settleTab`, on the day picked) or puts it on the guest's bill (`billToRoom`, then the bill is settled again).
- **Restaurant → Menu** (`MenuTab`, `/restaurant/menu`) is where the restaurant changes a dish's name or price, adds one, or takes one off. There is no Save button: a row is saved when it is left (`saveMenuItem`), and a dish taken off is set `active = false`, never deleted (`removeMenuItem`) — slips and recipes still point at it.
- **Restaurant → History** (`RestaurantHistory`, `/restaurant/history`, 2026-11-05) lists each order slip by day, newest first, and opens to its steps, latest first: ordered, served, taken off, sent to the front desk, sent to a room, sent back. The steps are rows in `tab_events`, written only by triggers on `tab_lines` and `tabs` (`20261105130000_order_slip_steps.sql`), so no order function or app path writes them; taps of one kind within 5 minutes are one step, and a hand-written sale is never logged. Every step is plain ink with its own icon — gold and green already mean something on the till (Sebastian); a row shows its three latest steps and a "+N" for the earlier ones, on the same columns as its opened steps. A diner's slip paid at the desk also has a **Paid** step, from its `payment_records` rather than `tab_events`, whose receipt number opens `TabReceiptModal` (2026-11-09); a slip on a room's bill has none.
- **The Restaurant's Orders screen is built for a tablet or a phone first, upright or sideways.** It fills the screen and only the menu scrolls (`isTill` in `DashboardLayout.tsx`). Three extra Tailwind screens in `tailwind.config.js` carry it: `wide:` (a PC, or a tablet held sideways — the slip sits beside the menu), `tall:` (the screen is tall enough to pin everything; otherwise the page scrolls), `mouse:` (a PC — the strip of guests wraps instead of sliding). Where it is not `wide`, the slip is `OrderDock` (a bar under the menu) opening `OrderSheet`; both and the side panel show the one `OrderSlipPanel`. Touch targets are 44px or more, and a text box is 16px so a phone does not zoom in on it.
- **Several staff use the system at once** — one at the front desk, one in the kitchen, one in the restaurant or bar — and they swap places. Every screen is open to all of them; do not hide a screen by role. A screen that others change must follow them live (`useRealtimeTabs`, `useRealtimeBookings`).
- **Booking sites' calendar links** (Booking.com, Airbnb; 2026-11-01, on development, not on live). `sync-ical` runs every 15 minutes from the database (`pg_cron`; the schedule in `20261031120000_booking_com_calendar_links.sql` names the project's URL, so live needs its own) and only ever adds through `add_channel_stay`; it never changes or removes a booking. A stay it added holds `bookings.channel_ref` (`channel|room it was sold on|in|out`), which stays the same when the desk moves the guest (`place_channel_stay`, `move_channel_ref`). What needs the desk is a row in `channel_alerts`: `clash` (a room sold twice: no booking exists yet, so `TimelineGrid` draws it on a second lane under the room and `calendar/SoldTwicePanel` answers it) and `gone` (off the link: the pill shows Cancelled and the panel asks; cancelling the booking closes the row). `calendar/ChannelBell` shows only while something waits. A stay with the placeholder name is "Name needed" (`needsDetails`, `calendar/ChannelDetails`) and has no figure or Bill until it has a name. `export-ical` reads `channel_export`: the room's nights from its half-days, reservations included, leaving out only what that site sold on that room. Both functions are deployed with `verify_jwt` off.
- **Stock** (`HousekeepingTab`, still at `/housekeeping`): Stock room · What a dish uses (`/housekeeping/dishes`) · Cleaning checklist (`/housekeeping/cleaning`).
- **The top bar is four tabs — Front desk, Restaurant, Inventory (it was "Stock"), Cash Flow (it was "Money"; both renamed 2026-10-14) — plus a Settings gear.** The list is `TABS` in `DashboardLayout.tsx`; a tab opens on its first screen and the rest are sub-tabs. A new screen goes inside a tab, never a fifth tab, and never in the bottom bar.
- `/reserve` (`PublicReservePortal`) is a public page outside the passcode gate.

### Updates reach open screens by themselves

Each build is stamped with a version, baked into the app and written to `/version.json` (`stampVersion` in `vite.config.ts`). `utils/appUpdate.ts` (started in `App.tsx`, only in a built app) asks for that file when the screen comes back into view and every 5 minutes; once it differs, the page reloads at a moment nobody loses anything — no portal open over the app, nothing saving, `isDeskBusy()` false, no focused box with words in it, and nobody has touched the screen for 90 seconds (or it is out of sight). There is no "please refresh" banner (Sebastian, 2026-10-30). An old page asking for a code chunk the update deleted (`vite:preloadError`) reloads at once, at most once in 30 seconds. A new kind of open window that is not a portal into `<body>` must tell `deskState` it is open, or an update could reload under it.

### New features mark themselves — every update that goes live adds one

Since 2026-11-05 a new or changed feature marks itself where it lives, in place of the "What's new" window (Sebastian: "add indicators from now on for features with updates or new features instead of using the what's new"). **Any push to `main` that changes what the staff see adds one entry to `NEW_FEATURES` in `src/utils/newMarks.ts`, in the same push** (`id` and the day it goes live as `since`). The feature wears a gold NEW tag (`<NewTag id=… />` in `components/NewMark.tsx`, its parent `relative`) and calls `markSeen(id)` when tapped — only tapped, never hovered. Only the feature is marked: no dot on the tab or the buttons that lead to it (Sebastian, 2026-11-05). One tap clears it on that device (`localStorage` `daweez_new_seen`, since there are no staff logins), and they go by themselves after 30 days. A change they cannot see needs no entry. The What's new window and its list were deleted on 2026-11-06.

## Conventions

- Tailwind only generates classes written as full literal strings; a class built by concatenation renders unstyled.
- Number inputs are free-typing (`NumInput`), never the browser number spinner.
- Printed documents: the guest statement is A5, the payment receipt is a 58 mm thermal slip (`.print-page` / `.print-slip` in `index.css`). Layouts that must hold on paper use fixed columns, not responsive breakpoints.
- Both can be emailed: `utils/emailDocument.ts` draws the paper on screen into a PDF and the `send-email` edge function posts it from the hotel's Gmail. The function needs the secrets `GMAIL_USER` and `GMAIL_APP_PASSWORD` on the Supabase project and counts its daily limit in `email_log`; Settings → Email (`settings/EmailSetup.tsx`) shows whether it is connected, the steps to connect it, and a test send.
- Code comments in this repo explain the owner's ruling or the bug that led to the code; keep that style when a change has such a reason.
