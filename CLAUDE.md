# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A staff system for **Daweez Pension House** (Tandag City, Philippines): 10 rooms and three venues (Vacation House, Gazebo, Garden Area). It replaces a paper booking process. Three parts, in priority order: **bookings** (closest to done), **restaurant and bar till**, **stock room**. The staff are not technical — every label is plain everyday English ("Total Money In", never accounting terms), the UI states facts without captions explaining them, and there are no browser `alert`/`confirm` pop-ups (use `showToast` and `askConfirm`).

React 19 + TypeScript + Vite, TanStack Router/Query, Tailwind 3 + DaisyUI, Supabase (Postgres, Realtime, three edge functions). Deployed on Vercel.

## Architecture

### How the app reaches the database

- The app uses the public anon key. "Login" is a passcode checked in the browser that sets a `localStorage` flag — there are no staff accounts yet (board card k74).
- **Bookings cannot be written directly.** anon has SELECT only; every write goes through SECURITY DEFINER functions: `book_booking`, `update_booking`, `cancel_booking`, `delete_booking`, plus narrow single-column writers (`set_booking_agreed_deposit`, `set_booking_stay_hours`, `undo_booking_check` — the last no longer called, since there is no check-in). Room prices and `app_settings` follow the same pattern. Tabs, menu, stock, expenses and agencies are written directly — except the lines on an order slip, which go through `apply_order_changes` (see Restaurant).
- **Ids are text** (`room-3`, `venue-gazebo`, `partner-…`). Never cast an id to `uuid` inside a database function. Only `tabs` and `tab_lines` use real uuids.
- Double booking is refused by exclusion constraints on `bookings`, counted in **half-days** (`booking_halves`, mirrored by `bookingHalves` in `utils/halfDays.ts` — change both together); the client check (`utils/availability.ts`) is only an early warning. Cancelled bookings are excluded from both.

### Booking data flow

`utils/db.ts` (reads/writes) → `utils/syncEngine.ts` (barrel re-export) → `hooks/useBookings.ts` (TanStack Query cache + mutations) → `DashboardContext` → tabs. `hooks/useRealtimeBookings.ts` patches the cache from Supabase Realtime.

- **A booking column must be added in four places:** the `Booking` type, `toBookingRecord` (db.ts), the reader in `getBookings` (db.ts), and `rowToBooking` (useRealtimeBookings.ts). The cached booking is what gets saved back, so a column missing from a mapper is wiped on the next save.
- **`update_booking` takes the whole row.** JSON columns sent as `null` are written as empty (the `COALESCE` in the function does not protect them). Any save path that builds a booking from scratch rather than from the cached row must carry over what it does not own — see the edit branch of `createManualBookingMutation`.
- The context exposes `bookings` (active stays; cancelled left out) and `allBookings`. Use `allBookings` only where cancelled bookings matter: the Front desk's History (`DeskHistory`), the daily money sheet, and receipt numbering.
- A booking of several rooms is **one row per room/venue, each with its own `invoice_number`** (the column is UNIQUE), tied together by a shared **`group_id`** written by `set_booking_group`. Ask `groupOf(booking, list)` (`utils/bookingGroup.ts`) which rooms belong together — the bill and the booking panel both do. The bill carries the first room's number. **Every room of a bill shows the bill's money** (`asBill`: the pill, its hover card and the panel's figure, 2026-10-20); each room still stores only its own balance and share, and a payment written on the bill is shared out across them (`payBill` in `ExtendStayModal`).

### Money

- **One pricing rule:** `calculatePricing` in `utils/pricing.ts`. Everything that re-prices a booking must pass every fact about it (breakfast, short-stay hours, discount, agency rate) or screens disagree. `recomputeBalance` in `utils/bookingBalance.ts` is the one place "what is owed" is worked out: stay + food tab − money received.
- Payment status is derived from recorded payments, never typed. Payments live in `bookings.payment_records` (JSON), each with a stored receipt number `PR-YYYYMM-NNN` that must be unique across all bookings and tabs.
- One payment for several rooms is stored on **every** room with the full `amount`; each room's own slice is `share` / `downpayment_paid`.
- Dates are built from **local** time parts (`dateToString`), never `toISOString()` — the hotel is UTC+8.
- `recomputeBalance` leaves a booking untouched when its room is not in the list it was handed (the page is still loading) and when it is a block. Do not re-price with an empty `rooms` array: `calculatePricing` falls back to built-in sample rooms.
- A stay **billed to an agency** (`isBilledToAgency`: has `partner_deal_id` or `company_name`) is not chased for money. It is left out of `isOwed` and listed under "Agencies owe". Plan `'agency'` ("Bill the agency") is no longer offered: since 2026-10-06 the form has three deposit choices for every booking — `custom` (shown as **Deposit** since 2026-10-21; half the stay filled in, with a note kept in `bookings.notes`), `full`, `reservation` (No deposit). `'agency'` and `'deposit'` are only read back from older bookings and shown as No deposit and Custom.
- A room's breakfast is charged once for each morning of its stay, or only for the mornings the desk picked on the bill (the Breakfast line's two dates, `MorningPick`, 2026-10-29), kept in `bookings.breakfast_days`. Ask `breakfastMornings` (`utils/breakfast.ts`): days outside the stay do not count, and none (or none left after the dates moved) is every morning. `calculatePricing` takes them as `breakfastDays`, so every caller that passes `breakfastIncluded` passes them too; the breakfast cup asks only on those mornings.
- Each morning's breakfast answer is `bookings.breakfast_choices`, written only by `set_booking_breakfast_choices` (`utils/breakfastChoice.ts`). It is a record, not a charge — never put it in `breakfast_records`, which the pricing rule bills. An answer with dishes on it is also the kitchen's order: `sent_at` is stamped when the desk presses Serve (`calendar/BreakfastPicker`), `KitchenTab` shows today's answers that have no `ready_at` as cards, and "Order ready" stamps it. Both live inside the JSON, so there is no column for them. **The owner's rule (2026-10-08): once a feature works, how it feels comes before everything else** — the breakfast window's moves (`bp-…` in `index.css`) are the model.
- **Today's money is a balance that carries over** (`buildDailyReport` in `utils/dailyReport.ts`, the one rule behind the screen and the printed sheet): its bottom bar is the staff's own paper summary, line for line — Cash for today (`totalIn`) · Add: Cash balance forwarded (`broughtForward`) · Cash on hand · Less: Expenses (`totalOut`) · Less: Cash remitted · Total cash on hand (`balance`). Money the staff hand to the owner is a row in `money_handovers` (`utils/handovers.ts`, `expenses/HandOverModal`): it comes off the balance but is **not an expense**, so nothing in the earnings report reads it. It is rare, so it is a quiet link under the day and its gold line shows only on a day it happened. Cash the staff put into the hotel ("Add cash on hand") is the same row with `kind = 'in'`: it adds to the balance and is never income. Each Money in line is a payment receipt (`MoneyInLine`, `PaymentLine` in `expenses/DayMoney`): a booking's opens its bill right there, being worked on (`calendar/WorkingBill`: the bill over its panel kept out of sight with `unseen`, since the payments go through the panel; the tapped payment is ringed, `mark` → `.bill-mark`, and folded payments open; the top bar's **Booking** (`onBooking` on `StatementShell`, not on a cancelled booking) hands the booking to the calendar through `focusBookingAfterCreate`, which opens its panel and pulses its pill), a diner's slip its receipt. Under Money out, a day's expenses of one category are one line with a count (`ExpenseGroup`, `byCategory` in `expenses/DayMoney`) that opens to every expense and its note; the printed sheet still lists each one. Lines sharing a receipt number are one payment across rooms, but a diner's slip is never joined to a booking's payment, and a room's receipt number is read fresh from the database (`freshReceiptNumber`) so it cannot take a slip's.
- **There is one bill, always being worked on** (Sebastian, 2026-10-24: "no more view billing or receive money. merge everything"). The panel's one **Bill** button, a statement found by search and a booking just made all open `calendar/NewBookingBill` with `editing` set, over the panel (`billOf` in `CalendarTab`). Each change is saved by itself (an 800 ms pause, one queue, `✓ Saved` on the top bar) through `submitBookingForm`; its payments go through the panel beneath it (`PanelDesk` on `deskRef`, so `payBill` shares them out), and the paper copy for Print and Email is a hidden `PrintInvoiceModal` (`.bill-paper`). It is never only looked at (Sebastian, 2026-10-28): a cancelled booking found by search opens it the same way. The bill's blank lines (`billing/BillDesk`): a payment is written on its blank line (what it was for — `PaymentRecord.purpose`, printed on the bill and the receipt — and the amount, then how they paid; always dated today) and a charge added under its rows (`event_addons.charges`, `BillCharge` — priced by `calculatePricing` like the add-ons). The statement's payment details, policies and signatures show only on paper (`data-paper`; the emailed copy shows them too). An agency's paper stays Total only.
- A block with no end date is an ordinary block whose `check_out` is `OPEN_END` (`utils/openBlock.ts`).

### Screens

- **Calendar** (`CalendarTab`) is the landing screen and the only way to start a booking: pick dates on the grid, then the action bar offers New booking / short stay / block / log old booking. The search button on its top line (`calendar/CalendarSearch`, 2026-10-24; "/" opens it) finds bookings by guest or room, billing statements by `invoice_number` and receipts by receipt number, cancelled ones too: a booking opens its panel on the calendar (`openFound` pulses its pill), a statement or a receipt opens its print window, and a cancelled booking opens its statement. `calendar/ExtendStayModal` is the booking panel: where the stay is, the money in one figure, the Bill button and Cancel. **There is no check-in or check-out** (Sebastian, 2026-10-20: on paper the staff only ever recorded the booking, the guest and the money, and the app must not change a booking by itself): where a stay is comes from its dates against today (`utils/stayStage.ts` — before, during, after; the arrival day is during, the leaving day after; a noted check-out makes it after at once, 2026-10-25), and early or late hours are a charge the desk adds to the bill. The desk may still note when a guest checked in or out — a black question mark at each end of the booking panel's stage line while it is not noted (no tick once it is), and the same question mark on a pill leaving today whose check-out is not noted, green at the start of a pill arriving today whose check-in is not noted (`AskDoor` in `TimelineCell`; on a half-day pill they sit on its top corners; a finished stay has no tick, 2026-10-24), from that day on (`BookingStageLine`, `utils/doorTimes.ts`, 2026-10-21) — saved in `actual_check_in` / `actual_check_out`; it changes nothing else, and a day gone by with nothing ticked reads as 2 PM / 12 PM without being saved. `update_booking` keeps a time sent blank, so taking one off calls `undo_booking_check` first. **Rescheduling, extending and changing rooms happen on the bill** (its dates and room line); the calendar way and Settings → Front desk were taken out on 2026-10-24 (the `front_desk` row in `app_settings` is no longer read). New booking opens a blank billing statement (`calendar/NewBookingBill`, saved through `submitBookingForm`; an agency or an institution turns it into the agency's statement), and Log old booking opens one too (`calendar/LogOldBill`, which saves nothing until Log booking). A pill's colour is the stage of the stay from its dates (`stayStage`: still to come, in its dates, over), and it says in words whether the stay is paid (Paid, Not paid, Part paid, Deposit paid, Agency pays) but never an amount (Sebastian, 2026-10-20; the amount is on the hover card). **A day is two half-columns** (morning, afternoon) and a stay runs from the afternoon of its check-in day to the morning of its check-out day (out 12 PM, in 2 PM), so one day can end a stay and begin the next. `calendar/timelineHalves.ts` says who fills each half; `TimelineGrid` walks a row half by half; a short stay is the exception and fills the half it was booked for (`bookings.stay_half`, 0 morning / 1 afternoon; 12 hours take that half and the next), so the other half of its day can be sold (2026-10-25): a single pick carries which halves are free, the action bar's Morning / Afternoon chip moves it, 12h shows only when the half after is free and Block only when a night fits. Its half pill shows the leave time under the initials. A late check-in keeps all its hours, so the stay reaches as far as they do; noting one that runs into the next booking is refused (the panel says so, and the database too) — the desk sorts it out, the app never moves the other booking. **A pill says where the stay is, not who: "Reserved" before its dates, "Occupied" during them, the guest's name once they are over** (`pillWords` in `TimelineCell`; the name is on the hover card and in the panel), or the agency's name (`company_name`) when there is one. **The calendar speaks in signs, and the words for them are in `calendar/CalendarGuide` (the `?` on the top line) — a sign added to the calendar is added to the guide in the same change:** a half-day pill shows the guest's initials (`pillInitials`); a stay in its dates is a soft green pill, not gold — the green is a wash inside the pill (`TimelineCell`), the room's bar is its own element that grows (`ROOM_BAR`), a pill's money words rise in when they change (`MoneyWords`), and the booking panel seals a finished payment (`mark` in `ExtendStayModal`); no payment recorded on a reservation or an agency's stay is the one thing said in words — “No deposit” in blue on the money line, blue initials on a half-day pill (`pillMoney` → `noDeposit`); a building icon is an agency; a cup that hops beside a room's name (`animate-hop`; a button that opens the breakfast picker) is a room with breakfast today that has not been asked yet, shown only until 11 AM (after that an unasked morning counts as nothing; `breakfastAskOpen`) and gone once it is asked — a room counts as in the hotel once a night of its dates has passed (`wantsBreakfastToday`) — and back in brown once the kitchen has cooked it (`ready_at` with no `served_at`; `breakfastReady` in `CalendarTab`), where one tap says it was served; a green bar on the room is a stay in its dates; and under each date are how many arrive and leave that day (`TimelineGrid`).
- **Restaurant** (`RestaurantTab`): the staff call a food bill an **order slip** (`OS-0001`); the tables are still named `tabs` and `tab_lines`, and they never live on the booking. A slip is numbered by its first order (a database trigger) and stays open until it is paid, so a stay holds several — read them with `utils/orderSlips.ts`, never one tab per booking. **No money is taken on the Restaurant screen** — everyone pays at the front desk: a room guest from the booking panel, which marks the slip paid (`paid_at`) and closes it; a diner with no room from "Diners to pay" on the calendar's top line (`calendar/TodayStrip`, which is now only that button, shown only while a bill the restaurant has sent over is waiting — a table still eating is not on it; `useDinerSlips`, `DinerPayModal`). **An order starts with a table the staff start, never with a room:** a table is not tied to a room while the order is taken. **The screen is the order slip beside the menu; the tables are put away behind the slip's title** (`restaurant/TablesPopup`: `TableButton` opens a grid of twelve numbered squares plus "Other", in the calendar pills' colours — white taking the order, gold in the kitchen, green left edge ready; a green bell on the button counts dishes ready on any table). A dish tapped with nobody picked opens the tables and goes onto the one chosen. **The popup holds only what the restaurant still has something to do with** (`served` in `RestaurantTab`, filtered from `people`, every open slip): a table from its first dish until its bill is sent; a slip that belongs to a room only while a dish on it has not been served (it is on the room's bill already); never a slip with nothing on it; always whoever is picked. A table started and left empty is closed again (`tidyAway`). **"Send bill" is the only hand-over** and it is where the room is asked for (`BillPicker`): to the front desk (`billOutTab`) or onto a room's bill (`billToRoom`, which gives the slip its `booking_id` then). Either stamps `tabs.billed_at` and closes the slip to more orders, so a closed slip is not always a paid one — ask `paid_at`. It cannot be pressed until a dish has been served, nor while one has not been sent to the kitchen (`canBill` in `TabBill` and `OrderDock`), and a room is confirmed by number and name. The slip (`TabBill`) is two groups, "To send" and "In the kitchen"; a line's number is its take-one-off button and a ready dish has its own "Serve". **No button on this screen waits for the server or greys out while it saves:** "Send to kitchen" and "Serve" lay `marks` over the lines, a sent bill is hidden through `billed`, a table being started titles the slip through `opening` (all in `RestaurantTab`), each saved behind and taken back if the save fails — do not add a `working`/`busy` flag that disables buttons. The menu marks a dish on the order with a gold bar and the single most ordered dish as "Best seller" (`readBest` in `MenuPicker`, summed from every `tab_lines` row — nothing is stored for it). The front desk prints the bill and can send a diner's slip back (`sendBackTab`); there is no way yet to take a bill off a room it was put on by mistake. There is no "Guest copy" in the restaurant: it has no printer. The booking panel has no "Take orders" (the owner, 2026-10-16): every order starts from a table. **A menu tap shows on the slip at once and is saved behind it:** `useTabOrder` keeps the taps as waiting changes, `withChanges` lays them over the saved lines, and one call to `apply_order_changes` (`utils/orderChanges.ts`) writes what was tapped together — it opens the stay's slip, adds the line or raises its count, and deducts the dish's recipe from stock. Never write `tab_lines` from the tablet one call at a time, and never lock the menu while saving. `useOpenSlips` reads every open slip with its lines in one query and throws away a read that an order overtook. **The order reaches the kitchen on a screen, never on paper:** "Send to kitchen" marks the lines sent, and the cook reads them on Restaurant → Kitchen (`KitchenTab`, `/restaurant/kitchen`, `useKitchenQueue` over the `kitchen_queue` view), which stays open on the kitchen's own device. A line counts four things in a row — `qty` → `sent_qty` → `ready_qty` → `served_qty` — each never more than the one before, written by `mark_order_lines_sent` / `_ready` / `_served`. The kitchen's list ignores whether the slip is still open: a guest who pays first still gets their food. A kitchen card is a checklist: a ticked dish is saved as cooked at once but stays on its card struck through (that memory is the screen's own, in `useKitchenQueue`) until the whole card is done; the waiting time turns gold at 10 minutes and red at 15 (`KitchenTab`).
- **Restaurant → Menu** (`MenuTab`, `/restaurant/menu`) is where the restaurant changes a dish's name or price, adds one, or takes one off. There is no Save button: a row is saved when it is left (`saveMenuItem`), and a dish taken off is set `active = false`, never deleted (`removeMenuItem`) — slips and recipes still point at it.
- **The Restaurant's Orders screen is built for a tablet or a phone first, upright or sideways.** It fills the screen and only the menu scrolls (`isTill` in `DashboardLayout.tsx`). Three extra Tailwind screens in `tailwind.config.js` carry it: `wide:` (a PC, or a tablet held sideways — the slip sits beside the menu), `tall:` (the screen is tall enough to pin everything; otherwise the page scrolls), `mouse:` (a PC — the strip of guests wraps instead of sliding). Where it is not `wide`, the slip is `OrderDock` (a bar under the menu) opening `OrderSheet`; both and the side panel show the one `OrderSlipPanel`. Touch targets are 44px or more, and a text box is 16px so a phone does not zoom in on it.
- **Several staff use the system at once** — one at the front desk, one in the kitchen, one in the restaurant or bar — and they swap places. Every screen is open to all of them; do not hide a screen by role. A screen that others change must follow them live (`useRealtimeTabs`, `useRealtimeBookings`).
- **Stock** (`HousekeepingTab`, still at `/housekeeping`): Stock room · What a dish uses (`/housekeeping/dishes`) · Cleaning checklist (`/housekeeping/cleaning`).
- **The top bar is four tabs — Front desk, Restaurant, Inventory (it was "Stock"), Cash Flow (it was "Money"; both renamed 2026-10-14) — plus a Settings gear.** The list is `TABS` in `DashboardLayout.tsx`; a tab opens on its first screen and the rest are sub-tabs. A new screen goes inside a tab, never a fifth tab, and never in the bottom bar.
- `/reserve` (`PublicReservePortal`) is a public page outside the passcode gate.

### What's new — every update that goes live adds an entry

The owner asked for a "What's new" on the Front desk after every update to the live system. **Any push to `main` that changes what the staff see adds one entry at the top of `UPDATES` in `src/utils/whatsNew.ts`, in the same push.** Its `id` is the day it goes live (`YYYY-MM-DD`, with a letter for a second update that day). It is written for the staff: what they can now do and on which screen, in plain everyday English, never what changed in the code. A change they cannot see needs no entry. `components/WhatsNew.tsx` shows it: the window opens by itself once on each device after an update, only on the Front desk's calendar and never over a panel the desk has open (the calendar and the top bar tell each other through `utils/deskState.ts`). It stays behind the "What's new" button in the top bar, beside Sync, with a dot until it is opened. What a device has shown is kept in its `localStorage` (`daweez_whats_new_seen`), since there are no staff logins.

## Conventions

- Tailwind only generates classes written as full literal strings; a class built by concatenation renders unstyled.
- Number inputs are free-typing (`NumInput`), never the browser number spinner.
- Printed documents: the guest statement is A5, the payment receipt is a 58 mm thermal slip (`.print-page` / `.print-slip` in `index.css`). Layouts that must hold on paper use fixed columns, not responsive breakpoints.
- Both can be emailed: `utils/emailDocument.ts` draws the paper on screen into a PDF and the `send-email` edge function posts it from the hotel's Gmail. The function needs the secrets `GMAIL_USER` and `GMAIL_APP_PASSWORD` on the Supabase project and counts its daily limit in `email_log`; Settings → Email (`settings/EmailSetup.tsx`) shows whether it is connected, the steps to connect it, and a test send.
- Code comments in this repo explain the owner's ruling or the bug that led to the code; keep that style when a change has such a reason.
