    - `bookings`: Active and pending customer bookings. Includes table constraints like `check_in < check_out`, status values, sequential invoice numbers, guest demographics, and corporate partner deal fields. Newer columns support the Daweez changes: `applied_discount` (jsonb), `early_check_in_hours`/ `late_check_out_hours` (int), `actual_check_in`/`actual_check_out` (timestamptz), `notes` (block reason), `prepared_by`, `payment_records` (jsonb receipts), `venue_day_blocks`, `breakfast_days` (jsonb), `breakfast_records` (jsonb per-day breakfast), `reference_number` (text) + `registered_on` (date) for old paper-log backfills, plus `payment_status`, `payment_plan` (text: `'deposit'` | `'full'` | `'custom'` | `'reservation'`) and `promo_applied`. **`agreed_deposit` (numeric)** holds the figure the guest agreed to hand over — half the stay for **Deposit**, the whole stay for **Full pay**, the amount the desk typed for **Custom**, and **NULL for a Reservation, which agrees to nothing** — worked out by `amountToPayNow`; NULL on a booking saved before this rule means "work it out", and the app then falls back to half the stay. It is written through `set_booking_agreed_deposit` rather than the booking RPCs.
    - `partner_deals`: Store corporate company, travel agency, and government contract profiles, default breakfast inclusions, default invoice styles, and room/venue rate overrides. **`id` is TEXT holding readable `partner-…` ids** (widened from uuid in `20260928162102`), and `bookings.partner_deal_id` matches it — an agency a booking names is stored as that same readable id.
    - `ical_feeds`: Subscribed iCal URLs for syncing Airbnb and Booking.com channels.
    - `app_settings`: The **shared staff settings**, one JSON object per key — `rate_config` (venue hourly, early/late charge, the breakfast menu, extras & rentals, security deposit, standard times), `payment_accounts` (the GCash number and **both** bank accounts printed on the bill) and `channel_sync` (the iCal master switch and the rooms taken off, `{ "enabled": true, "rooms": { "room-3": false } }`). **These lived only in one browser until 2026-09-28**: a second PC showed the factory defaults, and the account a guest was told to pay into could differ from the one on their printed bill. One key/value table rather than a column per setting because the app reads and writes each as a single object. Written **only** through `set_app_setting(text, jsonb)`, whose key is whitelisted so a stray call cannot invent a setting nothing reads — **adding a key therefore needs a migration**, and `channel_sync` was added by `20260930130000_add_channel_sync_setting.sql`. `channel_sync` is the one setting the **`sync-ical` edge function** reads as well as the app, which is deliberate: the switch has to bind the server that does the fetching.
- **Row-Level Security (RLS)**:
  - Public can select `rooms`; anon cannot modify them directly, so room rate edits go through the SECURITY DEFINER `update_room_rate` RPC (granted to anon + authenticated). `app_settings` follows the same shape: public SELECT, no anon write, and `set_app_setting(text, jsonb)` as the only way in — the shared settings are money-adjacent (venue hourly, the early/late charge, the accounts guests pay into) or operational (the iCal switches), so they are treated like a rate, not like the menu.
  - Public can SELECT `bookings` (availability checks) and has full access (ALL) to `ical_feeds` because the frontend PMS dashboard operates with the public/anon key and uses client-side passcode authentication. Direct anon INSERT/UPDATE/DELETE on `bookings` is revoked — every write goes through the SECURITY DEFINER RPCs above so arbitrary clients cannot edit or delete other people's bookings. `inventory_items`, `cleaning_checklist`, `menu_categories` and `menu_items` are also public full-access (consistent with the anon-key dashboard pattern) — those are all configuration, not money. `tabs` grants public SELECT/INSERT/UPDATE but **no DELETE** (a tab is closed, not removed), and `tab_lines` grants SELECT + INSERT + DELETE — a mistaken line is removed outright, the same rule the app applies to a wrong payment. **Neither table grants UPDATE on a line**, so a line is never rewritten in place: staff remove it and add the right one.
  - Authenticated managers have full access to `rooms`, `bookings`, and `ical_feeds`.
- **Edge Functions**:
  - `export-ical`: Serverless function exporting local reservation tables into standard `.ics` file format. Accepts either `room_id` (UUID) or `room_number` (integer) query parameters. Rewritten from `/api/ical/room/:room_number.ics` in the Vercel deployment.
  - `sync-ical`: Serverless function fetching, parsing, and updating local booking tables from subscribed external iCal feeds. Non-destructive and idempotent: it reconciles only sync-managed rows (deletes feed blocks no longer present, skips events that are already synced), and skips any event that overlaps an existing booking instead of forcing a double-booking. **Since v4 (2026-09-30) it honours the iCal switches itself**: it reads `app_settings.channel_sync` before fetching anything, skips every feed when the master is off, and skips a room the desk switched off — **on the server, because this function is what actually fetches**, so an old tab on another machine cannot sync a room that was switched off (that is exactly how nine feeds came to download the same Airbnb calendar nine times and import one reservation into all ten rooms). A room that is off is **left completely alone** — not fetched, and **not tidied either**, since the same run deletes sync rows a feed no longer lists. **The expired-`pending` cleanup at the end is deliberately NOT behind the master switch**: expiring an unpaid website hold is the app's own job, and switching the channels off must not leave abandoned holds blocking rooms. The response reports `channelsOn` and `skippedRooms` alongside the two counts.

## Work Guidance

- **Edge Function Runtime**: Target Deno runtime for edge functions. Keep external imports pinned to tested versions.
- **Migration Policy**: Ensure schema changes in `supabase/migrations/` are idempotent. Always declare indices for query optimization on check-in/check-out boundaries.
- **Security Check**: The frontend uses client-side passcode gate authentication and operates via the Supabase anon key, so RLS keeps `bookings` public-read and routes all writes through the SECURITY DEFINER RPCs (which enforce collision rules). `ical_feeds` still grants public write access to support feed updates. When adding new write paths, prefer an RPC + an exclusion-constraint backstop over granting direct table writes to `anon`.

- **Edge Functions**: Serve and test functions locally via `supabase functions serve`.
